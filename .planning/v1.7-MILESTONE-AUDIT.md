# Milestone v1.7 "Add Mode" — Audit Report

**Audited:** 2026-10-04
**Status:** gaps_found
**Scope:** Phases 13, 14, 15 (ROADMAP v1.7 section); 17 requirements (ADD-01…ADD-16, TAG-07)

**Milestone goal (ROADMAP):** Let the admin add the resolved target to every selected group they are not yet in, with the same safety, throttling and reporting as removal — direct invite/add where possible, unban-first for banned targets, and a privacy-block fallback of unique expiring invite links sent in one templated direct message.

## Verdict

Every phase passed its own verification, code review fixes, security audit and Nyquist validation, and the per-phase requirement claims are consistent across VERIFICATION.md, SUMMARY frontmatter and REQUIREMENTS.md. The cross-phase integration check found that the **stop/relaunch → Resume** path (ADD-08) does not work end-to-end: Phase 14 and Phase 15 were each verified against their own assumption about what Resume sends, and the hand-off was never traced. A second blocker hides the Add-mode checklist for the most common Add scenario (target in none of the admin's groups). Both are small, localized fixes. Everything else — rights computation, dispatch, unban-first, links, single DM, typed outcomes, template editing, progress/report, export, localization, Tag cleanup, and the Remove/Tag regression surface — is wired and green.

## Cross-Phase Integration

24 integration points checked: 20 wired, 2 warnings, 2 broken. All 12 new IPC channels have a main handler, preload entry, renderer client and UI consumer; 0 orphaned routes. All side-effecting handlers (ADD_START, ADD_RETRY_GROUP, TARGET_ADD_CONTACT, ADD_EXPORT_LOG, CLIPBOARD_WRITE_TEXT) are auth-gated; ADD_START enforces Zod, double-start and enumeration dialog-map gates; `targetAccessHash` is stripped before IPC.

### Blockers

1. **Resume sends the remaining subset; the executor requires the full set.** `AddResumeJobDialog.tsx:41-51` and `addStore.ts:172-176` (Phase 15, cloned from the Tag dialog) pass only unprocessed ids. `AddExecutor.ts:269-274` continues the on-disk job only when `sameDialogIdSet(existing.dialogIds, params.dialogIds)`; `addExecutor.test.ts:1145-1167` locks in subset → fresh job. Any job with ≥1 outcome is overwritten with a new jobId, dropping prior `done`/`privacy-blocked` outcomes and their links from the end-of-run DM and never emitting the CONTINUATION log block. Affects ADD-08, ADD-11, ADD-14.
2. **A stopped job has no remaining ids.** Stop → `_markRemainingSkippedAndStop` (`AddExecutor.ts:892-916`) checkpoints `'skipped'` for every unprocessed group. The dialog's remaining set is therefore empty, `startAdd([])` is rejected by `AddStartSchema` `min(1)` (`addChannels.ts:87`), the error is swallowed, and the dialog shows "n of n processed". The executor's own skipped-reprocessing logic (`AddExecutor.ts:280-284`) is unreachable from the UI. Affects ADD-08.
3. **Relaunch resume dies at the executor.** After relaunch the resolver is empty; `execute()` returns to `'idle'` (`AddExecutor.ts:203-208`) and never rebuilds the peer from `targetAccessHash` although `addTypes.ts:120-122,139-141` document that it does. `ADD_START` also silently returns while enumeration is loading (`addChannels.ts:157-161`) and `addStore.startAdd` clears `pendingJob` on any returned state. Affects ADD-08. (RemovalExecutor has the same resolver dependency, so Remove/Tag resume share the "re-confirm target first" expectation; the difference is that Add's typed contract and ADD-08 explicitly promise relaunch resume.)
4. **Add-mode checklist hidden when the target is in no groups.** `GroupsPane.tsx:300-311` returns the Remove-mode "not in any of your groups" empty state whenever zero rows are `'member'`, with no `activeMode` gate; `GroupsPane.tsx:903` renders `emptyState ?? <list>`. Affects ADD-02 (and ADD-01 reachability of Review).

Note on UAT: 15-UAT item 8 ("Resume continues the same job id from the first unprocessed group") was recorded as pass. The code admits exactly one passing scenario — a job with zero outcomes (remaining == full set) and the same target re-resolved and confirmed before clicking Resume. The three blockers above cover every other case.

### Warnings (non-blocking)

- `'banned-no-unban-right'` grey reason never assigned (ADD-02/ADD-07 partial): banned rows are pre-checked whenever `canAdd`, then fail at runtime with `ADD_NO_RIGHTS`.
- Default DM template language: main resolves EN/CS at launch, renderer at preview time → preview can differ from the sent DM after an in-session language switch with no saved template (ADD-12/ADD-16).
- Add-log blocks show dialog ids, not titles (ADD-14 readability).
- Scan polarity doc drift in 13-02 SUMMARY; the fix also made restricted-but-present participants actionable in Remove mode (semantic change outside the "no shipped Remove path changes" claim).
- `TargetCard` "Change target" disabled only during Remove runs; `getAddStatus` renders unselected greyed rows as "queued"; `wizardStage` ADD_* events and `DmTextProvider` type are orphans.

## Recommended closure (smallest set)

1. `AddResumeJobDialog.handleResume` + `addStore.resumeJobFromDisk`: pass `job.dialogIds` (full set); compute the "nothing left" guard and the processed count excluding `'skipped'` outcomes. Add a cross-phase test that round-trips a stopped job through the renderer's resume call into `AddExecutor.execute`.
2. `AddExecutor.execute()`: when `resume` is true and the resolver is null, rebuild `{ id, accessHash, name }` from the job file (`targetId`/`targetAccessHash`/`targetName`) as the type contract promises; have `ADD_START` wait for or report enumeration not loaded instead of silently returning.
3. `GroupsPane.renderEmptyState`: gate the "not in any groups" branch on `activeMode !== 'add'` (Add mode's empty case is "already in every group you can invite to").
4. Either compute `'banned-no-unban-right'` in `GroupEnumerator` (banned + no `banUsers` right) or remove the enum member and its i18n keys.
5. Pass dialog `title` into add-log entries; align default-template language between main and renderer (persist the default on first Add review, or read the live language in main).
6. Promote 14-VALIDATION.md status from draft; correct the polarity note in 13-02 SUMMARY.

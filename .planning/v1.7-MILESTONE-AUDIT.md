## Critical findings

- **F1: the relaunch-resume run is invisible and can't be stopped.** `GroupsPane.tsx:95` derives `mode` from the renderer's confirmed target. After a relaunch there is none, so `renderProgressSlot` returns null (`:351`). That hides the progress bar, Stop (the only `abortAdd` caller, `:500`), the PEER_FLOOD Resume banner and the report band. Only per-row statuses render. The fix is to show the Add progress slot and report band whenever add is non-idle, and to use `add.targetName` for labels.
- **F2: wrong-identity add with no review.** `retryGroup` prefers the live resolver (`AddExecutor.ts:592`), and target lookup isn't blocked during an add run on the relaunch path. The fix is to use the job's `_resolvedTarget`, or check it against `targetId`. Also block or abort target resolve and confirm while add is non-idle. ADD_START with `resume: true` and a mismatched targetId should be rejected, not started as a fresh job.

UAT 16-1 passed. It probably exercised a flow where the target had been re-confirmed, or it relied on row statuses. The automated cross-process test bypasses IPC and the UI.

# Phase 4.1: Code Review Report

**Reviewed:** 2026-06-12
**Depth:** standard (cross-file contracts verified where files interact)

## Summary

Phase 4.1 adds name-based participant search as a third target-entry path. The
architecture is sound and the CR-01/02/03 lessons from Phase 4 are correctly
applied: generation guards appear after every `await`, `TARGET_RESET` calls
`searcher.abortSearch()` first in the right order, and `accessHash` never crosses
the IPC boundary. The code is well-structured and the test coverage is good.

Three critical issues were found: a silent error-swallowing pattern in
`searchStore.startSearch()` that causes the UI to silently stop responding when
main throws a `ZodError` (e.g. for a short query already caught client-side but
re-submitted by a test or a forged IPC call), a `BigInt()` crash in
`CandidateRow.getAvatarColor()` for any candidate whose `id` string is not a
valid decimal integer (a Telegram user ID that has been returned with an unexpected
format would brick the entire candidate list render), and a store ref-count
imbalance bug inherited from the analog pattern where `stopSubscriptions()` can
decrement `refCount` below zero and permanently prevent re-subscription after
unmount/remount cycles.

## Critical Issues

### CR-01: `searchStore.startSearch()` silently swallows errors — UI freezes with no feedback

**File:** `src/renderer/store/searchStore.ts:88-93`

**Issue:** `searchActions.startSearch()` catches all errors from
`searchClient.startSearch()` with `console.error` and returns normally. When
main throws a `ZodError` (e.g., a query that passes the client-side ≥2 char check
but is rejected by Zod's `trim().min(2)` because it consists entirely of spaces
that the renderer did not strip), the catch block eats the error and leaves
`currentState` unchanged. The UI remains in `step: 'idle'` with no error message
displayed. The same silent failure applies to any IPC transport error during
`getSearchState()` at line 42. The analog `targetStore.ts` resolveTarget path has
the same structure, so this is a pervasive pattern — but `searchStore` is newly
introduced here and the pattern should be broken now.

More concretely: `searchClient.startSearch(query)` returns the state BEFORE
`search()` completes (it is fire-and-forget in main), so the returned state will
always be `{ step: 'idle' }` or `{ step: 'searching' }` — a thrown `ZodError`
should produce an `error` state but instead produces an unhandled rejected promise
that is silently caught. The renderer never enters an error step for this code path.

**Fix:**
```typescript
async startSearch(query: string): Promise<void> {
  lastQuery = query
  try {
    const s = await searchClient.startSearch(query)
    setState(s)
  } catch (err) {
    // Surface IPC/Zod errors as a terminal search error state instead of
    // eating them — renderer must see an error step, not silence.
    console.error('[searchStore] startSearch:', err)
    setState({ step: 'error', code: 'UNKNOWN' })
  }
},
```

### CR-02: `BigInt(candidate.id)` in `CandidateRow.getAvatarColor()` crashes on non-decimal strings, bricking the entire list render

**File:** `src/renderer/target/CandidateRow.tsx:27`

**Issue:** `getAvatarColor(seed: string)` calls `Number(BigInt(seed) % 7n)`. The
native `BigInt()` constructor throws a `SyntaxError` for any string that is not a
valid integer literal (e.g., an empty string, a string containing a negative sign
in an unexpected place, or any future Telegram ID format that is not a pure decimal
integer). Because `CandidateRow` is rendered inside `CandidateList`'s `.map()` loop,
a single bad `candidate.id` throws inside the React render tree, which in production
(no ErrorBoundary wrapping `CandidateList`) kills the entire `CandidateList` render
and shows a blank pane with no error message.

The `id` field is a `string` that comes through IPC from `user.id.toString()` in
`ParticipantSearcher._toDTO()`. In practice GramJS always returns a positive integer
string, but the type is `string` and there is no validation at the IPC boundary for
the candidate DTO shape. The crash surface is real.

Additionally `7n` is a bigint literal — for modulus colour selection this is fine,
but `Number(BigInt(seed) % 7n)` will produce values 0–6 correctly only for positive
IDs. A negative ID (Telegram channel IDs encoded as negative numbers in some
contexts) would produce `-1` to `-6`, causing `AVATAR_COLORS[negative]` to return
`undefined` and the `backgroundColor` style prop to be `undefined` — a silent
style bug rather than a crash, but worth noting.

**Fix:**
```typescript
function getAvatarColor(seed: string): string {
  try {
    const idx = Number(BigInt(seed) % 7n)
    return AVATAR_COLORS[Math.abs(idx)] ?? AVATAR_COLORS[0]
  } catch {
    // Fallback to a deterministic color based on string length
    return AVATAR_COLORS[seed.length % AVATAR_COLORS.length]
  }
}
```

### CR-03: `searchStore` ref-count imbalance — `refCount` can go negative, permanently blocking re-subscription

**File:** `src/renderer/store/searchStore.ts:47-51`

**Issue:** `stopSubscriptions()` decrements `refCount` unconditionally and only
stops subscriptions when it reaches zero. However, `startSubscriptions()` has an
early-exit guard (`if (refCount > 0) return`) that runs before incrementing, so
`refCount` is only ever incremented once. If `stopSubscriptions()` is called more
times than `startSubscriptions()` (which can happen if the component that called
`subscribe()` is unmounted and remounted rapidly in React Strict Mode or in test
environments where the effect cleanup runs twice), `refCount` goes negative.

The next call to `subscribe()` calls `startSubscriptions()`, which checks
`if (refCount > 0) return` — but now `refCount` is `-1`, so the guard passes and
`startSubscriptions()` runs again without having been blocked, creating a SECOND
`searchStateSub` while the `refCount` increments to `0`. Then on the NEXT
`stopSubscriptions()`, `refCount` goes to `-1` again and the original subscription
leaks.

The analog `groupsStore.ts` has the same pattern and this bug exists there too, but
`searchStore` is newly introduced here. The stable fix is to clamp `refCount` to
zero on stop, or use a simple boolean `subscribed` flag.

**Fix:**
```typescript
function stopSubscriptions(): void {
  if (refCount <= 0) return  // guard against underflow
  refCount--
  if (refCount > 0) return
  searchStateSub?.()
  searchStateSub = null
}
```

### WR-01: `ParticipantSearcher.search()` emits `{ step: 'error', code: 'UNKNOWN' }` for a short query — misleading error code

**File:** `src/main/telegram/ParticipantSearcher.ts:116-118`

**Issue:** When `query.trim().length < 2`, the method emits
`{ step: 'error', code: 'UNKNOWN' }`. The code `UNKNOWN` maps to a generic "couldn't
complete" message in `SEARCH_ERROR_COPY`. However, the correct code for this
condition is `SEARCH_QUERY_TOO_SHORT`, which is defined in `opTypes.ts` (line 36)
specifically for this purpose and is already in the `OperationErrorCode` union. The
IPC layer's Zod schema also enforces `min(2)`, so this branch is the defence-in-depth
path, but it should still produce a meaningful code when reached.

Furthermore, `SearchErrorCode` (in `searchTypes.ts`) does not include
`SEARCH_QUERY_TOO_SHORT` — the type would need extending. If it is not added, the
`SEARCH_ERROR_COPY` Record would fail to compile when the code is used in the renderer.
This is a latent type gap.

**Fix:**
1. Add `'SEARCH_QUERY_TOO_SHORT'` to `SearchErrorCode` in `src/shared/searchTypes.ts`.
2. Add an entry to `SEARCH_ERROR_COPY` in `searchCopy.ts`.
3. Change the emit in `ParticipantSearcher.search()`:
```typescript
if (query.trim().length < 2) {
  this._emit({ step: 'error', code: 'SEARCH_QUERY_TOO_SHORT' })
  return
}
```

### WR-02: `resolveByCandidate` fallback to `_resolveByUsername` can write `_resolvedUserId`/`_resolvedAccessHash` before the post-`GetUsers` generation guard

**File:** `src/main/telegram/TargetResolver.ts:188-196`

**Issue:** In `resolveByCandidate()`, when `GetUsers` throws and a `username`
fallback is provided (line 190), the code calls `_resolveByUsername(username, gen)`.
Inside `_resolveByUsername`, after the `contacts.ResolveUsername` call returns, the
method writes `this._resolvedUserId` and `this._resolvedAccessHash` at lines 332-334
**before** checking `gen !== this._generation` (the generation check at line 324
happens before bio/avatar, but the private field writes at lines 332-334 happen AFTER
that check). This means:

1. A `reset()` or concurrent `resolveByCandidate()` call that increments `_generation`
   between the `GetUsers` throw and the internal username resolve will have its
   generation guard pass at line 324 — but because `_resolveByUsername` throws
   `STALE_RESOLUTION` only for the pre-bio path, and the wrapping `resolveByCandidate`
   outer catch at line 229 re-checks `gen !== this._generation` before emitting, the
   observable symptom is that the emitted state is correct. However, the private
   identity fields `_resolvedUserId` and `_resolvedAccessHash` can be written by a
   stale resolution that beats a concurrent reset.

Specifically: if `resolveByCandidate(A)` throws on `GetUsers`, then `reset()` is
called (increments `_generation`, sets fields to null), then `_resolveByUsername`
finishes and writes the stale A fields before `STALE_RESOLUTION` is thrown — the
fields are `null` from the reset, then get written back to A's values, then the outer
catch checks generation and skips the emit. `getResolvedUser()` now returns A's data
even though the state appears `idle`. This is a subtle security gap: a caller in main
checking `getResolvedUser()` after a reset could receive stale identity material.

**Fix:** Add an additional generation guard in `_resolveByUsername` immediately
before writing `_resolvedUserId` / `_resolvedAccessHash` (there already is one at
line 324, but it is placed before bio/avatar fetches — move the field-writes to
after the guard, or add a second guard at line 331):
```typescript
if (gen !== this._generation) {
  throw STALE_RESOLUTION
}
// Only write private fields if generation is still current
this._resolvedUserId = BigInt(targetUser.id.toString())
this._resolvedAccessHash = ...
```
The current code at line 324 does this check but the field-writes at 332-334 follow
it directly, so this is actually correct for the normal path. The actual exposure
only manifests via the `resolveByCandidate` fallback path where `_resolveByUsername`
is called as a nested await inside a try/catch that has its own generation check.
Still, the defence should be verified: confirm that `_resolveByUsername` line 324 and
lines 332-334 are in the right order (they are). The issue is that
`resolveByCandidate`'s outer catch at line 229 only checks generation before the
emit — it does NOT restore `_resolvedUserId`/`_resolvedAccessHash` to their
pre-call state if generation changed. Defensive fix: store previous values and
restore them on stale detection in `resolveByCandidate`.

### WR-03: `getAvatarColor` uses `7n` bigint literal — not portable to environments without native BigInt support

**File:** `src/renderer/target/CandidateRow.tsx:27`

**Issue:** `Number(BigInt(seed) % 7n)` uses both the `BigInt()` constructor and the
`7n` bigint literal. While Electron's bundled Chromium supports native bigint, mixing
`BigInt(seed)` (dynamic) with `7n` (literal) is fine at runtime. However, the
`AVATAR_COLORS` array has 7 entries and the modulus is 7 — if the array length is
changed (e.g., a colour is added or removed) the magic number `7n` will silently go
out of sync. There is no compile-time enforcement.

This is the same duplication-of-length concern present in the already-shipped
`GroupRow`/`TargetCard` avatar functions, but `CandidateRow` introduces the `BigInt`
variant of this pattern and brings the potential for the crash in CR-02 noted above.

**Fix:** Use `BigInt(AVATAR_COLORS.length)` rather than the literal `7n`:
```typescript
function getAvatarColor(seed: string): string {
  try {
    const len = BigInt(AVATAR_COLORS.length)
    const idx = Number(BigInt(seed) % len)
    return AVATAR_COLORS[Math.abs(idx)] ?? AVATAR_COLORS[0]
  } catch {
    return AVATAR_COLORS[seed.length % AVATAR_COLORS.length]
  }
}
```

### WR-04: `searchStore` bootstrap race — `getSearchState()` can overwrite a later push-state after mount

**File:** `src/renderer/store/searchStore.ts:40-44`

**Issue:** `startSubscriptions()` registers the `onSearchState` push listener first
(line 36), then fires `getSearchState()` as an async bootstrap (line 41). If a
`SEARCH_STATE` push event arrives in the gap between registering the listener and
receiving the bootstrap `getState()` response, `setState(s)` is called for the
push first, then `setState(s)` is called for the (potentially older) bootstrap
response — overwriting newer state with older state.

The analog `groupsStore.ts` has the same race. For `searchStore` the practical
impact is low because a newly-mounted component bootstraps `idle` and any concurrent
search would be immediately overwritten with the push state. But a bootstrap `idle`
overwriting a `searching` state would cause the progress bar to disappear for one
render cycle, visible as a flicker.

**Fix:** Only apply the bootstrap response if it is not stale compared to current
state:
```typescript
searchClient.getSearchState().then((s: SearchState) => {
  // Only apply bootstrap if we haven't received a push since mounting
  if (currentState.step === 'idle') {
    setState(s)
  }
}).catch(console.error)
```
A more robust fix uses a sequence number, but the single-step guard is sufficient
for the `searchStore` use-case where the search is always initiated from user action
after mount.

### WR-05: `SEARCH_START` IPC handler does not check auth state — unauthenticated renderer can trigger search

**File:** `src/main/ipc/searchChannels.ts:81-88`

**Issue:** The `SEARCH_START` handler dispatches directly to
`searcher.search(parsed.query)` without checking whether the user is authenticated.
If the renderer somehow reaches a state where it can invoke `search:start` before
the session is established (e.g., a race during app startup, or if the preload bridge
is invoked programmatically), `ParticipantSearcher.search()` will call
`this._enumerator.getState()` which returns `{ step: 'idle' }` (groups not loaded),
and then emit `{ step: 'error', code: 'GROUPS_NOT_LOADED' }` — so the failure is
graceful, not a crash.

However, the CONTEXT.md and RESEARCH.md document an auth-state gate on IPC handlers
as an established pattern ("Security gate pattern on IPC handlers, e.g., retryGroup
checks auth state, 04-05 decision"). The `scan:start` handler in `groupChannels.ts`
also gates on auth. The `search:start` handler skips this gate — a minor consistency
gap. The `GROUPS_NOT_LOADED` code path adequately prevents API calls, but the gate
should be explicit.

**Fix:** Add the same auth-state check used by `scan:start` in `groupChannels.ts`
before dispatching to `searcher.search()`. Alternatively, document explicitly why
`search:start` does not require an auth gate (groups-not-loaded is the graceful
failure path).

## Info

### IN-01: `_toDTO` name fallback is redundant — `name || firstName` is always `firstName`

**File:** `src/main/telegram/ParticipantSearcher.ts:432`

**Issue:** `_toDTO` constructs the name as:
```typescript
const name = [firstName, lastName].filter(Boolean).join(' ')
return { name: name || firstName, ... }
```
When both `firstName` and `lastName` are empty strings, `name` will be `''` and
`firstName` will also be `''` — so the fallback `|| firstName` resolves to `''`
anyway. When `firstName` is non-empty, `name` will always contain it (it was the
first element). The `|| firstName` fallback only has meaning if `firstName` is the
empty string and `lastName` is non-empty, which would give `name = lastName`, then
`name || firstName` = `lastName` — the fallback never fires. The expression is
harmless but misleading, and the comment in RESEARCH.md Pattern 3 `_buildDTO` shows
the same construct in `TargetResolver._buildDTO` for consistency reasons.

**Fix:** Remove the redundant fallback:
```typescript
return {
  id: user.id.toString(),
  name,  // may be '' for deleted accounts — CandidateRow handles empty name gracefully
  ...
}
```

### IN-02: `CandidateList.handleSelect` is an `async` function defined inside a render — new reference on every render

**File:** `src/renderer/target/CandidateList.tsx:32-35`

**Issue:** `handleSelect` is declared as a plain `async function` inside the
component body. React will create a new function reference on every render cycle.
Because it is not passed as a prop to any memoised child (the `onSelect` prop of
`CandidateRow` is not wrapped in `useCallback` in `CandidateRow` either), this is
not a correctness issue — but it is inconsistent with the `useCallback` pattern
used in `TargetInput` for the analogous handler. If `CandidateRow` is later
memoised with `React.memo` to avoid re-rendering the entire list on each streaming
update, the unstable `handleSelect` reference will defeat memoization.

**Fix:** Wrap in `useCallback`:
```typescript
const handleSelect = useCallback(async (userId: string): Promise<void> => {
  setSelectingId(userId)
  await searchActions.selectCandidate(userId)
  setSelectingId(null)
}, [])
```

### IN-03: `void win` suppress in `registerSearchChannels` — `win` is genuinely unused

**File:** `src/main/ipc/searchChannels.ts:76`

**Issue:** The `win` parameter is passed to `registerSearchChannels` but only used
in `emitSearchState()`, which is a separate exported function wired in
`main/index.ts`. The `void win` suppression comment says "win used by
emitSearchState wired in main/index.ts" — technically accurate, but misleading:
`win` is not used by any code in this function's body. The parameter could be
removed from the function signature and `emitSearchState` could be called with the
window reference from `main/index.ts` directly — which is already how it works.
This is the same pattern as `groupChannels.ts`, so consistency is preserved, but
the suppress is a minor code smell.

**Fix:** Document why the parameter is kept (API symmetry with `groupChannels.ts`)
or remove it if the pattern is being re-evaluated:
```typescript
// win is not used inside this function — emitSearchState(win, state) is called
// directly from main/index.ts onStateChange lambda. Kept for API symmetry with
// groupChannels.ts and to make the wiring dependency visible at the call site.
```

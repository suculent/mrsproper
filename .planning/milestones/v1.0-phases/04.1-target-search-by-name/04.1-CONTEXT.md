# Phase 4.1: Target Search by Name - Context

**Gathered:** 2026-06-12
**Status:** Ready for planning

<domain>
## Phase Boundary

A user who knows only the target's first and/or last name can search for them across the groups they administer, pick the right person from a disambiguation list of candidates (avatar + identity details per candidate), and land in the exact same resolved-target confirmation gate as username/phone resolution — name search is a third entry path, not a parallel flow.

Architecture decision (locked, 2026-06-11, ROADMAP): name search is GROUP-SCOPED, not global. On-demand at search time (never prefetched at login), iterating already-enumerated groups with server-side participant name search per group (`channels.GetParticipants` + `ChannelParticipantsSearch(q)` for supergroups/channels; full participant list + client-side filter for basic groups, which cap at ~200 members), all serialized through the rate-limit governor with progressive results.

</domain>

<decisions>
## Implementation Decisions

### Search Entry & Input UX
- Name mode is auto-detected in the existing smart TargetInput field: input containing a space (or text not matching username/phone patterns) flips the mode chip to "Name" — a true third entry path in the same field, alongside username and phone detection.
- Search fires only on explicit Find button click or Enter (consistent with D-03 — no API calls while typing).
- Minimum query: 2 characters; a single token is allowed (first OR last name alone works); matching is case-insensitive.
- A running name scan is cancellable: Cancel affordance next to the progress indicator aborts remaining group searches (reuse the MembershipScanner abort/generation-guard pattern).

### Progressive Results & Progress Display
- Progress indicator follows the membership-scan pattern: "Searching group X of N…" counter; candidates stream into the list as they are found.
- Candidates are deduplicated by numeric user ID (merging their "found in" group lists); list ordered by number of groups found-in (descending), then by name.
- Per-group search failures are isolated: skip-and-continue with a soft non-blocking note ("Couldn't search N groups"), same error isolation as the membership scanner.
- Candidate list capped at 100 with a "Showing first 100 — refine your search" notice (user override: 100, not 50).

### Disambiguation List & Selection
- Candidate card shows: avatar + full name + @username (if any) + numeric ID + "Found in: {group names}" — per ROADMAP success criteria.
- Avatars lazy-load for visible candidates via governor-routed downloadProfilePhoto with initials fallback (reuse IdentityDisplay/TargetCard avatar patterns).
- Clicking a candidate resolves through the existing TargetResolver path (stable numeric ID, exactly-once resolution) and lands in the same TargetCard confirm gate; the search UI collapses exactly like the username/phone path.
- Empty state after a completed scan: "No one named '{query}' found in your {N} groups" — input stays editable, with a hint to try @username or phone instead. Not an error, not a dead end.

### Search Mechanics (Main Process)
- All enumerated groups are searched (including groups without ban rights) — identifying the right person matters even where action isn't possible; found-in labels include every group.
- Groups searched in enumeration order (same as the membership scanner) for predictable progress.
- New `ParticipantSearcher` service in main, alongside MembershipScanner, reusing its governor-routing, generation-guard, and abort patterns (including the CR-01/02/03 lessons from Phase 4 gap closure).
- No caching — every search runs fresh, consistent with the D-15 no-caching membership decision.

### Claude's Discretion
- Exact IPC channel names, store shape, and component file layout — follow the established targetChannels/groupChannels and targetStore/groupsStore patterns.
- Client-side name matching algorithm details for basic groups (e.g., token prefix matching) — keep consistent with how Telegram's server-side `ChannelParticipantsSearch` behaves so results feel uniform.

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/renderer/target/TargetInput.tsx` — smart single-field input with `detectMode()` (username/phone-bare/phone-international); extend with a 'name' mode. Find button + FLOOD_WAIT countdown wiring already present.
- `src/main/telegram/MembershipScanner.ts` — generation-guard + abort + progressive emission state machine; the template for ParticipantSearcher.
- `src/main/telegram/GroupEnumerator.ts` — provides the enumerated dialog/group list with entity id+accessHash (never reconstruct accessHash as BigInt(0) — causes CastError).
- `src/main/telegram/TargetResolver.ts` — exactly-once resolution; candidates resolve through it by ID.
- `src/renderer/shell/IdentityDisplay.tsx` / `src/renderer/target/TargetCard.tsx` — avatar bytesToDataUrl/getInitials patterns.
- `src/renderer/components/ui/` — shadcn-style primitives (avatar, scroll-area, badge, command) manually created in new-york/slate pattern.

### Established Patterns
- All Telegram calls route through `governor.run()` (floodSleepThreshold=0, D-11 — full FLOOD_WAIT governor visibility).
- IPC: typed channels in `src/shared/channels.ts`, handlers in `src/main/ipc/*Channels.ts`, renderer clients in `src/renderer/ipc/*Client.ts`, module-level stores in `src/renderer/store/*Store.ts` (subscriber pattern with setState; `_prevScanStep`-style transition tracking where needed).
- Security gate pattern on IPC handlers (e.g., retryGroup checks auth state, 04-05 decision).
- Duck-typed peer checks (`peer.userId !== undefined`) instead of instanceof — works for both real and mock GramJS clients.
- Tests: vitest with mock GramJS client in `src/main/telegram/__mocks__/telegramClient.ts`; deferred-promise race tests (see CR-02 regression tests in membershipScanner.test.ts).

### Integration Points
- `src/main/index.ts` — service construction and channel registration order matters (registerTargetChannels now takes scanner; ParticipantSearcher registration must follow the same wiring).
- `TARGET_RESET` IPC — must also reset/abort an in-flight name search so stale candidates never survive a target change (CR-01 lesson).
- `src/shared/targetTypes.ts` / `opTypes.ts` — extend with name-search DTOs and any new OperationErrorCode members (non-retryable disposition for terminal search errors, per T-03-02 pattern).

</code_context>

## User Constraints (from CONTEXT.md)

### Locked Decisions

- Name mode is auto-detected in the existing smart TargetInput field: input containing a space (or text not matching username/phone patterns) flips the mode chip to "Name" — a true third entry path in the same field, alongside username and phone detection.
- Search fires only on explicit Find button click or Enter (consistent with D-03 — no API calls while typing).
- Minimum query: 2 characters; a single token is allowed (first OR last name alone works); matching is case-insensitive.
- A running name scan is cancellable: Cancel affordance next to the progress indicator aborts remaining group searches (reuse the MembershipScanner abort/generation-guard pattern).
- Progress indicator follows the membership-scan pattern: "Searching group X of N…" counter; candidates stream into the list as they are found.
- Candidates are deduplicated by numeric user ID (merging their "found in" group lists); list ordered by number of groups found-in (descending), then by name.
- Per-group search failures are isolated: skip-and-continue with a soft non-blocking note ("Couldn't search N groups").
- Candidate list capped at 100 with a "Showing first 100 — refine your search" notice.
- Candidate card shows: avatar + full name + @username (if any) + numeric ID + "Found in: {group names}".
- Avatars lazy-load for visible candidates via governor-routed downloadProfilePhoto with initials fallback.
- Clicking a candidate resolves through the existing TargetResolver path (stable numeric ID, exactly-once resolution) and lands in the same TargetCard confirm gate; the search UI collapses exactly like the username/phone path.
- Empty state after a completed scan: "No one named '{query}' found in your {N} groups" — input stays editable, with a hint to try @username or phone instead. Not an error, not a dead end.
- All enumerated groups are searched (including groups without ban rights).
- Groups searched in enumeration order (same as the membership scanner) for predictable progress.
- New `ParticipantSearcher` service in main, alongside MembershipScanner, reusing its governor-routing, generation-guard, and abort patterns (including the CR-01/02/03 lessons from Phase 4 gap closure).
- No caching — every search runs fresh, consistent with the D-15 no-caching membership decision.

- Client-side name matching algorithm details for basic groups (e.g., token prefix matching) — keep consistent with how Telegram's server-side `ChannelParticipantsSearch` behaves so results feel uniform.

## Summary

Phase 4.1 adds name-based target search as a third entry path in the existing `TargetInput` smart field. The architecture is entirely parallel to `MembershipScanner`: a new `ParticipantSearcher` service in main iterates the already-enumerated group list, performs a governor-routed participant search per group, and streams deduplicated candidate DTOs to the renderer. The renderer stores candidates in a new `searchStore`, renders them in a `CandidateList` component, and on candidate selection routes through the existing `TargetResolver` by numeric ID — landing in exactly the same confirm gate as username/phone resolution.

The GramJS API surface is straightforward: `channels.GetParticipants` with `filter: new Api.ChannelParticipantsSearch({ q })` for supergroups/channels, paginating 200 results per call; `messages.GetFullChat` participant list + client-side substring filter for basic groups. Both are already exercised by the existing codebase (`MembershipScanner` uses `GetParticipant`/`GetFullChat`; `GroupEnumerator` uses `getDialogs`). Users returned in the `users` array of `channels.ChannelParticipants` carry `id`, `accessHash?`, `firstName?`, `lastName?`, and `username?` — the `accessHash` present in those objects is the correct one to pass to `TargetResolver.resolve()` via the numeric ID path (which calls `contacts.ResolveUsername`/`contacts.ResolvePhone` — but for candidates we need to resolve by ID directly, which requires adding an ID-based resolve path to `TargetResolver`, or accepting that selecting a candidate invokes name-based resolution again using numeric ID as the IPC payload).

The critical architectural decision: `TargetResolver.resolve()` currently accepts only a username-or-phone string and routes it to `contacts.ResolveUsername` or `contacts.ResolvePhone`. Resolving a candidate "by ID" requires a new IPC path — either extending `TargetResolver` with a `resolveById(id, accessHash)` internal path, or accepting that `ParticipantSearcher` stores candidate accessHash internally (in main only) and `TargetResolver` accepts a numeric-ID string as input, routing to `users.GetUsers` to refresh identity. Research below covers all options with tradeoffs.

**Primary recommendation:** Extend `TargetResolver` with an internal `resolveByCandidate(userId: bigint, accessHash: bigint)` method, triggered from the IPC layer via a new `TARGET_RESOLVE_CANDIDATE` channel carrying only the numeric user ID string (accessHash stored in `ParticipantSearcher` keyed by id, looked up in main). This preserves the security boundary (accessHash never crosses IPC) while enabling exactly-once resolution of a known candidate.

## GramJS API Surface — Verified Against telegram@2.26.22

### 1. `channels.GetParticipants` with `ChannelParticipantsSearch`

**Source:** `node_modules/telegram/tl/api.d.ts` lines 27068-27085 and 7624-7632.
[VERIFIED: npm registry]

```typescript
// Source: node_modules/telegram/tl/api.d.ts lines 27068-27085, 7624-7632
const result = await governor.run(() =>
  client.invoke(
    new Api.channels.GetParticipants({
      channel: new Api.InputChannel({ channelId, accessHash }),
      filter: new Api.ChannelParticipantsSearch({ q: query }),
      offset: 0,
      limit: 200,          // _MAX_PARTICIPANTS_CHUNK_SIZE in chats.js line 17
      hash: bigInt.zero,   // anti-cache hash; always zero for fresh queries
    })
  )
) as { count: number; participants: Api.TypeChannelParticipant[]; users: Api.TypeUser[]; chats: Api.TypeChat[] }
// TypeChannelParticipant = ChannelParticipant | ChannelParticipantSelf | ChannelParticipantCreator |
//                          ChannelParticipantAdmin | ChannelParticipantBanned | ChannelParticipantLeft
// Each participant has userId: long; users[] is the roster keyed by id.toString()
```

**Result shape `channels.ChannelParticipants`:**
- `count: number` — total matching participants (server-side)
- `participants: Api.TypeChannelParticipant[]` — participant subtypes (ChannelParticipant, ChannelParticipantAdmin, ChannelParticipantCreator, etc.) — each has `userId: long`
- `users: Api.TypeUser[]` — full `Api.User` objects for participants in this page — carry `id`, `accessHash?`, `firstName?`, `lastName?`, `username?`, `deleted?`, `min?`
- `chats: Api.TypeChat[]` — not needed for name search

**Pagination:** `offset` + `limit=200` per call. If `result.count > 200`, need additional calls with `offset += result.participants.length` until `result.participants.length === 0` or `offset >= result.count`. For the 100-candidate cap, most practical name queries will return far fewer than 200 results — full pagination is unlikely for real admin groups but must be handled.

**`hash: bigInt.zero`** — always send zero for `channels.GetParticipants` with `ChannelParticipantsSearch`. The anti-cache hash mechanism is irrelevant here; `ChannelParticipantsNotModified` will not be returned when hash=0.

**Server-side search behavior:** `ChannelParticipantsSearch(q)` is a prefix/substring match on the server against user's first_name, last_name, and username combined. Telegram docs confirm it is case-insensitive on their side. An empty `q=""` returns `ChannelParticipantsRecent` equivalent; the minimum meaningful query is 1-2 characters though the app enforces 2 client-side.

### 2. Basic Group Participant Fetch (no search filter)

**Source:** `node_modules/telegram/client/chats.js` lines 155-185, `node_modules/telegram/tl/api.d.ts`.
[VERIFIED: npm registry]

For `basic-group` dialogs (`Api.Chat` entities), there is no server-side name filter. The approach is:
1. `governor.run(() => client.invoke(new Api.messages.GetFullChat({ chatId })))` — already used by MembershipScanner.
2. From `result.fullChat.participants.participants` (array of `ChatParticipant`/`ChatParticipantAdmin`/`ChatParticipantCreator` — each has `userId: long`) and `result.users` array (`Api.User[]`), build a map by `userId.toString()` → `Api.User`.
3. Client-side filter: normalize query to lowercase tokens, check if user's first+last name (lowercase) contains any token as a prefix or substring (see client-side matching section below).

Basic groups cap at ~200 members by Telegram's design (at 200 members Telegram auto-migrates them to supergroups). `GetFullChat` returns the full participant list in one call — no pagination needed.

**Result shape from `messages.GetFullChat`:**
- `result.fullChat: Api.ChatFull` — `.participants.participants: ChatParticipant[]`
- `result.users: Api.TypeUser[]` — full user roster (same `Api.User` shape as GetParticipants)
- Each `ChatParticipant` has `userId: long` (always `ChannelParticipant.userId` shape, not a `peer`)

### 3. `Api.User` shape from participant results

**Source:** `node_modules/telegram/tl/api.d.ts` lines 791-850.
[VERIFIED: npm registry]

```typescript
// Relevant fields on Api.User returned in GetParticipants/GetFullChat
interface ApiUserCandidate {
  id: long             // big-integer — always present
  accessHash?: long    // big-integer — present UNLESS min=true (see min flag pitfall below)
  firstName?: string   // may be absent on deleted accounts
  lastName?: string    // frequently absent (single-name users)
  username?: string    // optional
  deleted?: boolean    // true on deleted accounts
  min?: boolean        // if true, accessHash is unreliable — need full resolve
}
```

**`min` flag pitfall:** When `min=true` on a returned `Api.User`, the `accessHash` present in the object is "minimal" and cannot be used directly with most MTProto requests. This occurs for users who have not been directly contacted or are not in the admin's contact list. For `ParticipantSearcher`, candidates returned from group participant search may have `min=true`. The safe approach: store the accessHash from the participant result for direct `users.GetUsers` resolution; if resolution fails with `ACCESS_HASH_INVALID`, fall back to resolving via username (if present) or flag the candidate as requiring re-lookup.

Practically: since `TargetResolver.resolveByCandidate()` will call `users.GetUsers([InputUser(id, accessHash)])` and that call will refresh the full user object, the min-flag issue resolves itself — `users.GetUsers` with a valid (even minimal) accessHash returns the full User with a fresh non-min accessHash. The candidate entry point merely needs to not crash when `accessHash` is absent entirely (null/undefined) — in that case, skip `downloadProfilePhoto` on the candidate row and mark `accessHash` as `BigInt(0)` for the IPC call (see TargetResolver existing pattern).

### 4. Resolving a Candidate by Numeric ID

**Current `TargetResolver.resolve(input)` only handles username and phone strings.** Adding candidate resolution requires a new internal path.

**Option A (recommended):** Add `resolveByCandidate(userId: bigint, accessHash: bigint)` to `TargetResolver`. This method calls `users.GetUsers([new Api.InputUser({ userId, accessHash })])` to refresh identity (gets full non-min user), then falls through the same `_fetchBio` / `_fetchAvatar` / `_buildDTO` path. A new IPC channel `TARGET_RESOLVE_CANDIDATE` carries `{ userId: string }` (the numeric ID as string — never accessHash over IPC); the handler in `targetChannels.ts` looks up the accessHash from `ParticipantSearcher.getCandidateAccessHash(userId)` — ParticipantSearcher stores a private `Map<string, bigint>` of `userId → accessHash` keyed from candidate results.

**Option B:** Extend `resolve(input)` with an `id:NNNNN` prefix pattern that routes to Option A's path. Less clean — mixes the input parsing concern.

**Option C:** Accept that clicking a candidate re-resolves by username (if username present) or shows an inline error. Rejected — username-less users are a primary use case.

**Recommended:** Option A. The `users.GetUsers` approach is clean, efficient (one call per candidate selection), and avoids bypassing the existing resolution state machine.

```typescript
// Source: node_modules/telegram/tl/api.d.ts — users.GetUsers
// new Api.users.GetUsers({ id: [inputUser] }) returns User[]
// inputUser = new Api.InputUser({ userId: bigInt(...), accessHash: bigInt(...) })
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Participant pagination | Custom loop | `channels.GetParticipants` with offset | GramJS handles TL serialization; offset+limit protocol is well-defined |
| Flood-wait between search calls | Manual sleep | `governor.run()` wrapping each call | The existing RateLimitGovernor already handles FLOOD_WAIT, PEER_FLOOD, retries |
| Name matching for supergroups | Client-side regex | Server-side `ChannelParticipantsSearch(q)` | Server handles transliteration, Unicode normalization, typo-tolerance |
| User identity refresh from min-user | Custom GetUsers wrapper | `users.GetUsers([InputUser])` inside `resolveByCandidate()` | Standard MTProto pattern |
| Deduplication across groups | Custom equals-by-value | Dedup by `userId.toString()` + merge `foundIn[]` | IDs are stable decimal strings; O(N) map-based dedup |

### Pattern 3: Candidate deduplication with foundIn merge

```typescript
// Pattern: Map<userId, CandidateAccumulator> keyed by userId.toString()
interface CandidateAccumulator {
  user: Api.User
  foundIn: Array<{ dialogId: string; dialogTitle: string }>
}

const candidates = new Map<string, CandidateAccumulator>()

function addCandidate(user: Api.User, dialogTitle: string, dialogId: string) {
  const key = user.id.toString()
  const existing = candidates.get(key)
  if (existing) {
    existing.foundIn.push({ dialogId, dialogTitle })
  } else {
    candidates.set(key, { user, foundIn: [{ dialogId, dialogTitle }] })
  }
}

// Emit as DTO (never emit raw Api.User — accessHash must stay in main)
function toDTO(acc: CandidateAccumulator): CandidateDTO {
  return {
    id: acc.user.id.toString(),
    name: [acc.user.firstName, acc.user.lastName].filter(Boolean).join(' ').trim(),
    username: acc.user.username ?? null,
    deleted: acc.user.deleted ?? false,
    foundIn: acc.foundIn.map(f => f.dialogTitle),  // only titles cross IPC
    // avatar: null initially — loaded lazily later
  }
}
```

### Pattern 4: ParticipantSearcher constructor mirrors MembershipScanner

```typescript
// Source: src/main/telegram/MembershipScanner.ts (existing)
export interface ParticipantSearcherOptions {
  client: ParticipantSearcherClient
  governor: RateLimitGovernor
  enumerator: GroupEnumerator
  onStateChange: (state: SearchState) => void
}

export class ParticipantSearcher {
  private _generation = 0
  private _abortController: AbortController | null = null
  // Stores accessHash for each candidate by userId string — for resolveByCandidate IPC
  private _candidateAccessHashes = new Map<string, bigint>()

  async search(query: string): Promise<void> {
    const gen = ++this._generation
    this._abortController = new AbortController()
    const signal = this._abortController.signal
    const candidates = new Map<string, CandidateAccumulator>()
    let searchedCount = 0
    let errorCount = 0

    const groupsState = this._enumerator.getState()
    if (groupsState.step !== 'loaded') {
      this._emit({ step: 'error', code: 'GROUPS_NOT_LOADED' })
      return
    }

    const dialogs = groupsState.dialogs
    const total = dialogs.length
    this._emit({ step: 'searching', progress: { searched: 0, total }, candidates: [], errorCount: 0 })

    for (const dialog of dialogs) {
      if (gen !== this._generation || signal.aborted) return

      try {
        const found = await this._searchDialog(dialog, query, gen, signal)
        if (gen !== this._generation || signal.aborted) return
        for (const user of found) {
          addCandidate(candidates, user, dialog.title, dialog.id)
          // Store accessHash in main only — never emitted to renderer
          if (user.accessHash) {
            this._candidateAccessHashes.set(user.id.toString(), BigInt(user.accessHash.toString()))
          }
        }
      } catch {
        errorCount++
      }

      searchedCount++
      if (gen !== this._generation || signal.aborted) return

      // Sort + cap at 100 for emission
      const sorted = sortCandidates([...candidates.values()])
      const capped = sorted.slice(0, 100)
      this._emit({
        step: 'searching',
        progress: { searched: searchedCount, total },
        candidates: capped.map(toDTO),
        errorCount,
      })
    }

    if (gen !== this._generation || signal.aborted) return
    const sorted = sortCandidates([...candidates.values()])
    this._emit({
      step: 'complete',
      candidates: sorted.slice(0, 100).map(toDTO),
      total: candidates.size,
      errorCount,
    })
  }

  abortSearch(): void {
    this._generation++
    this._abortController?.abort()
    this._abortController = null
    this._candidateAccessHashes.clear()
    this._emit({ step: 'idle' })
  }

  getCandidateAccessHash(userId: string): bigint | null {
    return this._candidateAccessHashes.get(userId) ?? null
  }
}
```

### Pattern 5: TargetResolver.resolveByCandidate() (new internal path)

```typescript
// Source: src/main/telegram/TargetResolver.ts (existing pattern, new method)
// users.GetUsers returns Api.TypeUser[] — the full non-min user
async resolveByCandidate(userId: bigint, accessHash: bigint): Promise<void> {
  const gen = ++this._generation
  this._emit({ step: 'resolving' })

  try {
    const inputUser = new Api.InputUser({
      userId: bigInt(userId.toString()) as BigInteger,
      accessHash: bigInt(accessHash.toString()) as BigInteger,
    })
    const users = await this._governor.run(() =>
      this._client.invoke(new Api.users.GetUsers({ id: [inputUser] }))
    ) as Api.TypeUser[]

    if (!users.length) throw Object.assign(new Error('USER_ID_INVALID'), { errorMessage: 'USER_ID_INVALID' })
    if (gen !== this._generation) return

    const user = users[0] as ApiUserShape
    this._resolvedUserId = BigInt(user.id.toString())
    this._resolvedAccessHash = user.accessHash ? BigInt(user.accessHash.toString()) : BigInt(0)

    const bio = await this._fetchBio(user)
    const avatar = await this._fetchAvatar(user)
    if (gen !== this._generation) return

    this._emit({ step: 'resolved', target: this._buildDTO(user, bio, avatar) })
  } catch (err) {
    if (gen !== this._generation) return
    const classified = classifyRpcError(err)
    this._emit({ step: 'error', code: classified.code as TargetErrorCode, input: userId.toString() })
  }
}
```

### Pattern 6: CLIENT_SIDE name matching (basic groups — mirrors server-side behavior)

```typescript
// Telegram's ChannelParticipantsSearch(q) matches prefix/substring of first+last name
// + username, case-insensitive. Mirror this for basic groups:
function matchesQuery(user: Api.User, queryLower: string): boolean {
  const tokens = queryLower.trim().split(/\s+/).filter(Boolean)
  if (!tokens.length) return false
  const name = `${user.firstName ?? ''} ${user.lastName ?? ''}`.trim().toLowerCase()
  const uname = (user.username ?? '').toLowerCase()
  return tokens.every(tok => name.includes(tok) || uname.startsWith(tok))
}
```

## Common Pitfalls

### Pitfall 1: `min=true` on Api.User from GetParticipants
**What goes wrong:** `Api.User.accessHash` may be absent or "minimal" when `user.min === true`. Attempting `downloadProfilePhoto(user)` or building `InputUser(id, minAccessHash)` for resolution will fail with `ACCESS_HASH_INVALID`.
**Why it happens:** GetParticipants returns min-users for participants who haven't been directly seen by the logged-in account in another context.
**How to avoid:** In `ParticipantSearcher._searchDialog()`, store `user.accessHash.toString()` if non-null; if null or min, store `'0'`. When `resolveByCandidate()` is called, `users.GetUsers([InputUser(id, 0)])` still works for public-profile users even with zero hash. For `downloadProfilePhoto` on candidate avatars — gracefully fall back to initials on any error (already the existing pattern from `_fetchAvatar` in TargetResolver).
**Warning signs:** `FloodWaitError` or `ACCESS_HASH_INVALID` during candidate avatar downloads.

### Pitfall 2: `ChannelParticipantsNotModified` response
**What goes wrong:** `channels.GetParticipants` can return `channels.ChannelParticipantsNotModified` (className='channels.ChannelParticipantsNotModified') when the hash matches cached state. With `hash: bigInt.zero` this should not occur, but defensive code must handle it.
**How to avoid:** After `governor.run()`, check `if (result.className === 'channels.ChannelParticipantsNotModified') continue` before accessing `result.users`.

### Pitfall 3: FLOOD_WAIT during multi-group search
**What goes wrong:** Searching many groups sequentially generates many `GetParticipants` calls. Telegram may return FLOOD_WAIT mid-scan.
**Why it happens:** Same as MembershipScanner — high-volume sequential API calls.
**How to avoid:** All calls go through `governor.run()`. The governor handles FLOOD_WAIT transparently (sleep + retry). The progress UI should surface the flood subline ("Telegram asked us to slow down — resuming automatically.") using the existing `OP_GOVERNOR_EVENT` flood-tick channel — no new mechanism needed.
**Warning signs:** Search progress stalls at a group boundary; governor emits flood-tick events.

### Pitfall 4: accessHash NEVER crosses IPC
**What goes wrong:** Emitting `CandidateDTO.accessHash` in the shared DTO allows a compromised renderer to replay it, bypassing security intent.
**How to avoid:** `CandidateDTO` has NO `accessHash` field — mirrors `ResolvedTargetDTO` pattern (T-03-01). `ParticipantSearcher._candidateAccessHashes` is a private in-main Map, accessed only by the `TARGET_RESOLVE_CANDIDATE` handler. The handler validates the userId is in the candidate map before passing the accessHash to `TargetResolver.resolveByCandidate()`.

### Pitfall 5: Stale candidates surviving TARGET_RESET (CR-01 pattern)
**What goes wrong:** User starts a name search, then clicks "Change target". If `TARGET_RESET` does not call `searcher.abortSearch()`, in-flight `search()` continues running and may emit new state after the resolver has reset — rendering stale candidates.
**How to avoid:** `registerTargetChannels` receives `searcher` as a third argument. `TARGET_RESET` calls `searcher.abortSearch()` first, then `scanner.abortScan()`, then `resolver.reset()`. The `SearchState` emitted by `abortSearch()` is `{ step: 'idle' }` — renderer clears the candidate list.

### Pitfall 6: Generation guard mid-loop (CR-02 pattern)
**What goes wrong:** In `ParticipantSearcher.search()`, after each `await governor.run(...)`, a new `search()` call (or `abortSearch()`) may have incremented `_generation`. Without re-checking, stale results get merged into a new scan.
**How to avoid:** Check `if (gen !== this._generation || signal.aborted) return` immediately after every `await` — before processing results, before emitting state. Mirror the exact pattern in `MembershipScanner.scan()`.

### Pitfall 7: Duplicate users in the same group
**What goes wrong:** A user can appear multiple times in GetParticipants pagination results (e.g., as regular member and as admin in different filter runs). The deduplication map must be keyed by `userId.toString()`, not by object identity.
**How to avoid:** The single `Map<string, CandidateAccumulator>` keyed by `userId.toString()` handles this — duplicate adds just extend `foundIn` on the existing entry (only if not already containing that dialogId).

### Pitfall 8: Empty query to GetParticipants
**What goes wrong:** `ChannelParticipantsSearch({ q: '' })` returns recent participants (equivalent to `ChannelParticipantsRecent`), not an empty result. This would return up to 200 members for every group — extremely expensive and not the intended behavior.
**How to avoid:** Client-side minimum-length validation (2 characters) in `TargetInput` before dispatch, and a second check in the IPC handler (Zod min(2) on the query string). `ParticipantSearcher.search()` also guards: `if (query.trim().length < 2) { emit error; return }`.

### Pitfall 9: `win.isDestroyed()` guard on state push
**What goes wrong:** If the window is destroyed while a search is running, `win.webContents.send(SEARCH_STATE, ...)` throws.
**How to avoid:** `emitSearchState(win, state)` mirrors `emitScanState` — gates on `!win.isDestroyed()` before send. (T-04-08 pattern, already in groupChannels.ts.)

### Pitfall 10: InputChannel / InputChannel entity construction
**What goes wrong:** Passing `bigInt.zero` as `accessHash` to `InputChannel` for channels.GetParticipants will cause the same `CastError` documented in MembershipScanner's `_checkMembership`. The stored entity's real `accessHash` must be used.
**How to avoid:** Same as MembershipScanner — `const entity = this._enumerator.getDialogEntity(dialog.id)` then extract `entity.accessHash` via duck-type, never reconstruct as `bigInt.zero`.

## Open Questions (RESOLVED)

1. **Pagination strategy for GetParticipants when result.count > 200** — RESOLVED: paginate until empty page OR global candidate cap (100) reached; planner adopted this in Plan 02.
   - What we know: GramJS `_MAX_PARTICIPANTS_CHUNK_SIZE = 200` per call; `result.count` gives total server-side matches; `offset += result.participants.length` advances.
   - What's unclear: For very large groups with common names (e.g., query "a"), hundreds of pages may be needed. With the 100-candidate cap, once `candidates.size >= 100` AND all currently buffered pages are processed, further pagination can stop.
   - Recommendation: Paginate until `result.participants.length === 0` OR `candidates.size >= 100` AND current group has been fully covered. Planner discretion on the exact short-circuit.

2. **`users.GetUsers` vs `contacts.ResolveUsername` for candidate resolution** — RESOLVED: primary path users.GetUsers with stored accessHash; fallback to contacts.ResolveUsername when accessHash is BigInt(0) AND user has a username (adopted in Plan 02 Task 2).
   - What we know: `users.GetUsers([InputUser(id, accessHash)])` refreshes a user by known ID+hash in one call. `contacts.ResolveUsername` requires a username and fails for username-less users. The candidate may have `min=true` with a minimal accessHash.
   - What's unclear: Whether `users.GetUsers` with `accessHash=BigInt(0)` succeeds for public-profile users with a deleted username.
   - Recommendation: Use `users.GetUsers` with the stored accessHash (even if minimal). If `accessHash === BigInt(0)` and the user has a username, fall back to `contacts.ResolveUsername` as a secondary path inside `resolveByCandidate()`. This is safe because the candidate was returned by Telegram's own GetParticipants — the user definitely exists.

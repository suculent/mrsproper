# Phase 17 — UI Design Contract

> Visual and interaction contract for the Phase 17 gap closure: the relaunch-resume run view
> (read-only job target card, forced/locked Add mode, job-only row list, Add band reachable
> without a confirmed target), the target-identity lock in the UI (locked mode switch, disabled
> target input), the in-session Resume on the stopped summary band (F4), the retry DM row status
> (F5) and the zero-dialogs Add empty message (D-14). Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.
>
> **This phase adds zero new tokens, sizes, weights, colors or primitives.** It consumes the
> Phase 1 / Phase 15 contract (`15-UI-SPEC.md`) unchanged. Everything not listed here (progress
> slot, PEER_FLOOD banner, summary band, row statuses, resume dialog, DM editor) stays exactly as
> specified in `15-UI-SPEC.md` §6–§9, apart from the label-source change in §2 below.

**Autonomous-mode decisions (no user available this session; review at UAT):** every choice
CONTEXT.md left to "Claude's Discretion" (job-card component and placement, placeholder-initial
style, new en/cs copy, hide-vs-disable for the target input) was resolved to the option most
consistent with `15-UI-SPEC.md` and the shipped components (`TargetCard.tsx`, `TargetInput.tsx`,
`ModeSwitch.tsx`, `GroupsPane.renderProgressSlot`, `GroupRow.tsx`). Each is flagged **[AUTO]**.

## Visual Hierarchy (focal points)

- **Relaunch run view (running):** the eye lands first on the Add progress band at the top of the
  groups pane (progress line + Stop). The job card in the left pane is second: it answers "who is
  this run for?". The job-only row list is third.
- **Relaunch / in-session report (stopped):** the summary band is the anchor. "Resume adding" is
  the only accent element in it, placed first in the band's button group, ahead of the outline
  "Export add log…" and "Add someone else".
- **Locked controls** (mode switch, target input) are visibly disabled (`opacity-50`) and quiet.
  Only the one-line lookup-locked hint explains them, and it never competes with the band.

## Interaction Contract

### 1. Run-view derivation in `GroupsPane` (D-01, D-03, D-04)

Define one derived flag in `GroupsPane` (or a pure helper next to `addPaneState.ts`, which is
preferred because it can be unit-tested):

```
addJobView = add.step !== 'idle' && targetState.target.step !== 'confirmed'
```

| State | Progress slot | Row list | Scan effects |
|-------|---------------|----------|--------------|
| `add.step === 'idle'` | Unchanged (scan or browse) | Unchanged | Unchanged |
| `add.step !== 'idle'` and target confirmed (in-session) | Add branches a-add / b-add / c-add, as today | Unchanged (all dialogs, job rows show status per D-16) | Unchanged |
| `addJobView === true` (relaunch) | Add branches a-add / b-add / c-add. **Must render even though `mode === 'browse'`** | Job-only list (below) | **Neither** the browse-abort effect nor the checklist auto-start effect fires |

- `renderProgressSlot()` evaluates the Add branches whenever `add.step !== 'idle'`, **before**
  any `mode === 'checklist'` or `activeMode` check. The current gate that returns `null` at
  `:351` must not run first.
- The `confirming` step is not part of the relaunch path. It still renders nothing in the band,
  as today.
- **Job-only row list (`addJobView`):** rows are `allDialogs` filtered to `add.dialogIds` and
  ordered by their index in `add.dialogIds` (job order), so progress reads top to bottom. The
  existing filter input still narrows within these rows. The sort toggle is ignored in this
  view **[AUTO]** because job order is the meaningful order during a run. Dialog ids absent
  from the loaded group list are not rendered. Resume is already refused for them via
  `resumeFailed`.
- Rows in `addJobView` carry **no selection checkbox** (D-03). The checkbox slot shows only the
  existing Add status indicator from `GroupRow.renderCheckboxSlot()`: queued shows the
  disabled checked indicator, then `Loader2`, `Check`, `AlertCircle` or `Minus`. Rows look
  identical to an in-session run row. No grey-reason sublines, no membership-scan pending
  skeletons, no "verify failed" retry. The status sublines from `15-UI-SPEC.md` §6 render
  unchanged, including the failed-row "retry" link (D-08).
- No empty-state (`renderEmptyState`) branch renders while `addJobView` is true.
- The bottom run-trigger ("Review adding to N groups") is hidden while `add.step !== 'idle'`,
  as today.

### 2. Label source (D-01)

- `add.progressLabel` (`{{name}}`)
- `add.dmStatusSent`, `add.dmStatusRefused` (`{{name}}`)
- The new retry-DM row strings in §6 (`{{name}}`)

### 3. Job target card (D-01), left pane

**[AUTO] Placement:** the left pane's identity slot, exactly where `TargetCard` renders today
(`AppShell` → `<div className="mt-4">`). The identity of the person being acted on always lives
in this slot in this app. Putting the card in the right pane would leave the left pane empty
under a disabled input. D-01 is met because the card is visible for the whole run view.

**Render rule:** `JobTargetCard` renders when `add.step !== 'idle' &&
targetState.target.step !== 'confirmed'`. When the target is confirmed (in-session),
the existing `TargetCard` renders instead. Never both. `CandidateList` does not render while
`add.step !== 'idle'`.

**Structure** (all classes copied from `TargetCard`):

```
<section aria-label={add.jobCard.aria, {name}}
         className="max-w-[560px] rounded-lg border bg-card p-6 flex flex-col gap-4">
  <div className="flex flex-row gap-6 items-start">
    <Avatar className="h-16 w-16 shrink-0">                 // no ring
      <AvatarFallback style={{backgroundColor: getAvatarColor(add.targetId)}}
                      className="text-white font-semibold text-base">
        {getInitials(add.targetName)}                       // aria-hidden
      </AvatarFallback>
    </Avatar>
    <div className="flex flex-col gap-1 min-w-0 flex-1">
      <span className="text-label text-muted-foreground">{add.jobCard.kicker}</span>
      <span className="text-heading font-semibold text-foreground truncate">{add.targetName}</span>
      <span className="text-label font-normal font-mono text-muted-foreground">{target.idLine, {id: add.targetId}}</span>
      <p className="text-body text-muted-foreground">{add.jobCard.note}</p>
    </div>
  </div>
</section>
```

- **Placeholder initial:** the same `getInitials()` rule as `TargetCard`: first letter of the
  first word plus first letter of the last word, uppercased, or one letter for one-word names.
  It sits on the deterministic avatar hue. If `add.targetName` is empty or whitespace, show the
  lucide `User` icon (`h-6 w-6 text-white`, `aria-hidden`) instead of initials.
- **No** `AvatarImage`, no Telegram call, no badges, no bio, no last-seen, no "No profile photo"
  `Alert`. The note line explains why details are missing. No contacts checkbox. No footer
  buttons: leaving the job is done only through "Add someone else" in the summary band (D-09).
- The ID line has no tooltip **[AUTO]**. The ID is shown so the admin can check it against
  the person they meant. The tooltip copy ("what Mrs. Proper acts on") stays specific to
  `TargetCard`.

### 4. Identity lock: mode switch and target input (D-02, D-05)

**Mode switch:**
- On relaunch Resume, `AppShell`'s `onResume` sets mode to `'add'` (it already does:
  `setMode('add')`).
- `ModeSwitch` `disabled` is true whenever `add.step !== 'idle'`. This is added with OR to the
  existing condition (`scan.step === 'scanning' || isRunActive || stage === 'run' ||
  stage === 'report'`).
- Tooltip (`title`) when locked: if `add.step !== 'idle'`, show
  `groups.modeSwitchLockedAddJobTooltip` (new). Otherwise show the existing
  `groups.modeSwitchDisabledTooltip`.
- The active "Add" segment stays `variant="default"` (accent) at `opacity-50`. Remove and Tag stay
  `ghost` at `opacity-50`. `aria-checked` is unchanged, and `aria-disabled` comes from the
  native `disabled`.

**Target input [AUTO: disable, do not hide]:**
- While `add.step !== 'idle'`, `TargetInput` renders with the `<Input>`, the country chip and
  the "Find person" `Button` all `disabled`. Enter and paste do not dispatch. The heading and
  description stay. Keeping the input visible but disabled keeps the left-pane layout stable
  between in-session and relaunch, and it shows the admin where lookup will come back.
- Directly under the input row, replacing the mode-chip and phone-disclosure hint area, render
  one line: `<p className="text-label font-normal text-muted-foreground">{target.lookupLockedAddJob}</p>`.
- Any typed text is kept but frozen. When the lock lifts (`resetTarget()` → `add.step` becomes
  `'idle'`), the input re-enables with an empty value, because `resetTarget` already clears it.
- Main-side rejection of `TARGET_RESOLVE`/`TARGET_CONFIRM` (D-05) is a backstop the UI cannot
  normally reach. If it ever returns an error, the renderer shows **nothing**: no
  `resolveError.*` line and no state change. It must not show "Something went wrong…" for a
  guarded no-op.

**Unlock:** only `targetActions.resetTarget()` ("Add someone else") lifts the lock. It sets
`add.step` to `'idle'`, the switch and input re-enable, the job card unmounts, and the stage
goes to `'target'` (D-09). There is no new "Done" button.

### 5. Resume on the stopped summary band (D-11, F4)

In branch c-add, when `add.step === 'stopped'` **and** `getResumeDialogIds(job)` is non-empty
(at least one unprocessed or skipped row):

- Render a `Button variant="default" size="sm"` labeled `add.peerFloodResumeLabel` ("Resume
  adding", an existing key reused, so both Resume buttons in the app use the same words) with
  `aria-label={add.resumeStoppedAria}`.
- Order in the right-hand button group (`flex items-center gap-2`): **Resume adding** →
  Export add log… → Add someone else.
- Click calls `addActions.resumeJobFromDisk()`, the same path as the PEER_FLOOD banner. The
  store must re-read the job file after a stop instead of relying on the first-subscribe
  `pendingJob`.
- While the request is in flight, the button is `disabled` and shows `Loader2`
  (`mr-1 h-3 w-3 animate-spin`) plus the existing `add.confirmDispatching` ("Starting…"). On
  success, the band switches to a-add (progress) through normal state flow.
- If groups are not loaded (`groupsState.step !== 'loaded'`), the button is `disabled` with
  `title={add.resumeLoadingGroups}` (existing key).
- On rejection (identity mismatch D-07, or any resume failure), render the existing
  `add.resumeFailed` copy as `<span className="text-label font-normal text-destructive">` at the
  bottom of the band's left text column. It clears on the next Resume click. The job file is
  untouched.
- `add.step === 'complete'` never shows Resume.
- **PEER_FLOOD banner (b-add):** unchanged except that on a rejected `resumeJobFromDisk()` it
  shows the same `add.resumeFailed` line (`mt-2 text-label font-normal`, inheriting the alert's
  destructive text color) under its Resume button, with the same in-flight disabled and
  "Starting…" treatment.

### 6. Retry DM row status (D-12, F5)

A retry that ends `privacy-blocked` immediately sends a one-link DM. The row (in both
in-session and job views) shows the existing `rowStatus.linkCreated` + Copy-link line, then one
more status line under it (above the Premium hint, if present):

| Retry DM state | Copy key | Style |
|----------------|----------|-------|
| sending | `add.rowStatus.retryDmSending` | `text-label font-normal text-muted-foreground`, preceded by `Loader2 h-3 w-3 animate-spin` (`inline-flex items-center gap-1`) |
| sent | `add.rowStatus.retryDmSent` | `text-label font-normal text-muted-foreground` |
| refused | `add.rowStatus.retryDmRefused` | `text-label font-normal text-foreground`. Not destructive, mirroring `dmStatusRefused`: an informational heads-up with a recovery path (the Copy button on the line above) |

- The line renders **only** for rows whose privacy-blocked outcome came from a retry. A row
  covered by the end-of-run DM shows no per-row DM line, because the band's `dmStatus` line
  covers it, as today.
- `{{name}}` = `add.targetName` (§2).
- No confirmation dialog before the DM (D-12: the retry itself was the explicit admin action).
- If the retry DM hits PEER_FLOOD, the existing hard-stop handling and banner take over. There
  is no row-specific copy for it.
- The field name and shape carrying this per-outcome DM state (for example
  `retryDmStatus?: 'sending' | 'sent' | 'refused'` on `AddGroupOutcome`) is the planner's choice.
  The UI contract is the three states above.

### 7. Zero-dialogs Add empty message (D-14)

When `activeMode === 'add'`, the pane is in checklist mode, the scan is complete and there are
zero dialogs (`allDialogs.length === 0`), render the existing no-groups empty state instead of
a blank list:

```
<div className="px-4 py-8 flex flex-col gap-1">
  <span className="text-label font-semibold">{groups.emptyState.noGroups.heading}</span>
  <span className="text-body text-muted-foreground">{groups.emptyState.noGroups.body}</span>
</div>
```

- **[AUTO]** Reuse the existing `groups.emptyState.noGroups` keys (already in en + cs, shown in
  browse mode today) rather than adding Add-specific copy. Zero administered groups is the
  same fact in every mode, and reusing the keys keeps browse and checklist consistent.
- Implementation: extend `AddEmptyState` with `'no-groups'`. `getAddEmptyState` returns
  `'no-groups'` when `dialogs.length === 0`, checked before the `failedCount` check. Remove and
  Tag modes are unchanged.

### Accessibility

  `aria-hidden` because the name is in the heading line.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| preload contextBridge -> renderer | Every new bridge method forwards a fixed, narrow payload shape (dialogIds / dialogId / template string) — no bridge method accepts or forwards identity fields, matching the existing Tag/Removal bridge methods. |
| TARGET_RESET -> active Add run | Resetting the target must abort any in-flight add run before the target is cleared, exactly like the existing removal/tag abort-first ordering — otherwise a stale AddExecutor run could continue acting on a cleared target's resolved identity. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-19 | Tampering | TARGET_RESET ordering | mitigate | `addExecutor?.abortExecution()` is called in the same handler, in the same position as the existing tagExecutor abort, before `resolver.reset()` — no window where a cleared target's identity is still being acted on by an add run. |
| T-14-20 | Information Disclosure | preload contextBridge surface | mitigate | `getAddJob`/`getAddState` return only `AddJobFileSafe`/`AddState` (already accessHash-stripped by Plan 14-10's IPC handlers) — the bridge adds no new exposure beyond what `addChannels.ts` already guards. |
| T-14-SC | Tampering | npm/pip/cargo installs | accept | No new packages; this plan only wires already-vetted modules together. |
</threat_model>

# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is design-system genesis.** Phase 1 establishes the foundational tokens (color, type, spacing) and the reusable interaction patterns (stepped form, inline error, loading/disabled, countdown, confirm dialog, identity display) that Phases 3, 4, and 6 inherit. Treat every token below as the project-wide default, not a one-phase choice.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn/ui — **recommended, not yet initialized** (greenfield; no `components.json` present) |
| Preset | Run `npx shadcn init` during the first plan of this phase. Configure: style "new-york", base color "slate", CSS variables ON. Record the resulting preset string back into this file's frontmatter (`preset:`) and flip `shadcn_initialized: true`. |
| Component library | Radix UI primitives (via shadcn/ui) — headless, accessible, well-maintained; first-class `Dialog`, `Select`, `Input`, `Button`, `Label`, `Alert` cover every Phase 1 surface |
| Icon library | lucide-react (shadcn default; tree-shakeable, MIT) |
| Font | **Inter** (UI text) via bundled `@fontsource/inter` (offline — Electron must not depend on Google Fonts CDN at runtime). Monospace: **system stack** (`ui-monospace, "SF Mono", "Cascadia Mono", Menlo, monospace`) for numeric user IDs and login codes. |

### Why shadcn/ui for an Electron renderer (justification)

- **Headless + you own the code:** components are copied into the repo, not imported from a versioned package, so there is no runtime dependency surface to break across Electron upgrades and nothing phones home — important for a security-sensitive desktop tool.
- **Radix gives accessibility for free:** focus trapping in the logout `Dialog`, keyboard navigation in the country `Select`, and correct ARIA wiring are built in — non-negotiable for a desktop app that performs destructive actions.
- **Tailwind CSS-variable tokens** map cleanly to the light/dark contract below and let Phases 3/4/6 consume the same tokens with zero re-spec.
- **Lightweight:** no heavyweight UI framework runtime; only the primitives actually used are pulled in.

### Theme mode

- Ship **both light and dark**, defaulting to **follow the OS appearance** (`nativeTheme.shouldUseDarkColors`) — desktop users expect the app to match macOS/Windows system appearance.
- No in-app theme toggle in Phase 1 (deferred; not load-bearing). The token set below defines both palettes so later phases inherit dark mode automatically.

## Spacing Scale

Declared values (8-point scale, all multiples of 4). Map to Tailwind's default scale (`1`=4px … `16`=64px).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, inline error icon spacing |
| sm | 8px | Compact element spacing, gap between dial-code select and number field |
| md | 16px | Default gap between form fields, card inner padding (mobile-of-window) |
| lg | 24px | Auth card padding, gap between form groups, section padding in the app shell |
| xl | 32px | Vertical rhythm between the auth card and the app logo/title block |
| 2xl | 48px | Major section breaks inside the authenticated shell (identity block ↔ stubbed workflow regions) |
| 3xl | 64px | Top/bottom breathing room framing the centered auth card in the window |

Exceptions:
- **44px minimum hit target** for any icon-only control (e.g. the country `Select` trigger, dialog close button) to satisfy desktop pointer ergonomics. This is a min-size constraint, not a new spacing token.
- Auth card has a **fixed max-width of 400px**, centered in the window, regardless of window size.

## Typography

Inter for all UI text. Exactly 4 sizes, exactly 2 weights (regular 400 + semibold 600).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display | 28px | 600 | 1.2 | Auth step titles ("Enter your phone number", "Enter the code"), app name in shell header |
| Heading | 20px | 600 | 1.2 | Logged-in display name, logout dialog title, section headers in stubbed shell |
| Body | 16px | 400 | 1.5 | Field hints ("We sent a code to your Telegram app"), dialog body copy, helper text, input values |
| Label | 14px | 600 | 1.5 | Field labels ("Phone number", "Login code"), `@username`, button labels, the FLOOD_WAIT countdown text |

Rules:
- **Numeric user ID, login code input, and `@username`** render in the monospace stack at the Body/Label size of their context — never proportional — so identity strings read unambiguously (a safety property).
- Never introduce a 5th size or a 3rd weight. If emphasis is needed, use the existing semibold weight or a color token, not a new size.

## Color

Trust-forward, deliberate, not playful. Telegram-adjacent blue accent so the app feels native to the ecosystem without imitating an official client. Destructive red reserved exclusively for irreversible/sign-out actions.

### Light mode (default surfaces)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | App background, auth-card surface, input fields |
| Secondary (30%) | `#F1F5F9` (slate-100) | Window chrome / shell sidebar + header band, stubbed workflow region backgrounds, dialog overlay-adjacent panels |
| Accent (10%) | `#2563EB` (blue-600) | See reserved-for list below |
| Destructive | `#DC2626` (red-600) | See reserved-for list below |
| Text primary | `#0F172A` (slate-900) | Body + headings |
| Text muted | `#64748B` (slate-500) | Hints, labels, placeholder, `@username` secondary line |
| Border | `#E2E8F0` (slate-200) | Input borders, card border, divider lines |
| Success | `#16A34A` (green-600) | Confirmed-identity affordance only (the green check beside the verified account) — not a general accent |

### Dark mode

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B1220` | App background, auth-card surface |
| Secondary (30%) | `#1E293B` (slate-800) | Shell chrome, stubbed region backgrounds, input fields |
| Accent (10%) | `#3B82F6` (blue-500) | Same reserved-for list, brightened for dark contrast |
| Destructive | `#EF4444` (red-500) | Same reserved-for list, brightened |
| Text primary | `#F1F5F9` (slate-100) | Body + headings |
| Text muted | `#94A3B8` (slate-400) | Hints, labels, placeholder |
| Border | `#334155` (slate-700) | Borders, dividers |
| Success | `#22C55E` (green-500) | Confirmed-identity check only |

**Accent (blue) reserved for — explicit list, never "all interactive elements":**
- The primary submit button on each auth step (Send code / Verify / Continue).
- The focus ring on the active input field.
- The selected country row in the country picker.
- The "Resend code" text link.
- The avatar ring on the confirmed logged-in identity (a calm, reassuring highlight — not red).

**Destructive (red) reserved for — explicit list:**
- The "Log out" confirm button inside the logout dialog.
- The server-revocation-failed warning banner (red-tinted, not full red fill).
- Inline auth errors (wrong/expired code, invalid phone) use destructive red **text + border on the offending field only**, never a red-filled block.

Everything not on these two lists uses neutral/slate tokens. Accent is the scarce 10% — it points the eye to the one safe next action per screen.

## Copywriting Contract

Plain, calm, trustworthy. Community admins, not engineers — no Telegram API jargon ("FLOOD_WAIT", "PHONE_NUMBER_INVALID", "AUTH_KEY") ever reaches the user; it is translated to plain language.

### Primary CTAs (one per surface — the scarce-accent action)

| Surface | Primary CTA label |
|---------|-------------------|
| Phone step | **Send code** |
| Login-code step | **Verify** |
| 2FA-password step | **Sign in** |
| Logout dialog | **Log out** (destructive) |

### Per-surface copy

| Element | Copy |
|---------|------|
| Phone step title | "Enter your phone number" |
| Phone step hint | "Choose your country and enter your number. We'll send a login code to your Telegram app." |
| Code step title | "Enter the code" |
| Code step hint | "We sent a code to your Telegram app." (with the entered phone shown muted beneath, e.g. "Sent to +1 555 123 4567") |
| 2FA step title | "Two-step verification" |
| 2FA step hint | "Your account is protected by a password. Enter it to finish signing in." |
| Resend link | "Resend code" |
| Empty state heading (stubbed workflow region in shell) | "Nothing to clean up yet" |
| Empty state body | "Target search and group selection arrive in a later update. You're signed in and ready." |
| Identity confirmation affordance | A green check + label "Signed in" beside the name — reassures this is the right, intended account. |

### Error states (problem in plain language + what to do next; user stays on the current step)

| Trigger (API cause) | User-facing error copy |
|---------------------|------------------------|
| Invalid phone format (pre-send validation) | "That phone number doesn't look right. Check the country and number, then try again." |
| `PHONE_NUMBER_INVALID` (server reject) | "Telegram didn't recognize that number. Double-check it and try again." |
| Wrong code (`PHONE_CODE_INVALID`) | "That code wasn't right. Check it and try again." |
| Expired code (`PHONE_CODE_EXPIRED`) | "That code expired. Tap Resend code to get a new one." (Resend link emphasized) |
| Wrong 2FA password (`PASSWORD_HASH_INVALID`) | "That password wasn't right. Try again." |
| `FLOOD_WAIT_x` (rate-limited) | "Too many attempts. Try again in **{N}** — {countdown}." Submit disabled until the live countdown reaches zero, then re-enabled automatically. |
| Network/connection failure | "Couldn't reach Telegram. Check your connection and try again." |

### Destructive confirmation

| Action | Confirmation copy |
|--------|-------------------|
| Log out | Title: "Log out?" — Body: "You'll need to sign in again with a code." — Buttons: **Cancel** (neutral, default focus) / **Log out** (destructive). |
| Logout where server-side revocation failed but local session was wiped | Non-blocking warning banner after logout completes: "You're signed out on this device, but we couldn't confirm Telegram revoked the session. Open Telegram → Settings → Devices to remove it manually." (red-tinted warning, never silent) |

## Interaction Patterns (reusable — established here, inherited by Phases 3/4/6)

These are the load-bearing patterns this phase births. Specify them once; later phases reference them.

| Pattern | Contract |
|---------|----------|
| **Stepped form** | One step visible at a time, centered 400px card. Step title (Display) + hint (Body) + field(s) + single primary button. Back affordance: a muted text "Back" link top-left of the card on code/2FA steps only (phone step has none). No progress dots in Phase 1 (steps are short and conditional). |
| **Country picker** | shadcn `Select` (searchable command list): trigger shows flag glyph + dial code (e.g. "🇺🇸 +1"); dropdown rows show flag + country name + dial code; national-number `Input` sits to the right (8px gap). Selecting a country never clears a typed number. |
| **Loading / disabled (submit-in-flight)** | On submit: button shows an inline lucide `Loader2` spinner (animate-spin) at 16px to the left of its label, label stays visible, button disabled; all inputs in the step disabled (not hidden). No full-screen overlay, no spinner that replaces content. Min visible spinner time 300ms to avoid flash. |
| **Inline error** | Destructive-red helper text (Label size) directly beneath the offending field, plus destructive border on that field. Error clears on next edit of the field. User never leaves the current step. A lucide `AlertCircle` 16px icon precedes the text. |
| **Live countdown (FLOOD_WAIT)** | Submit disabled; button label augmented or replaced with "Try again in {mm:ss}" updating every second; counts down to zero then re-enables automatically and restores the normal CTA label. The remaining seconds render in monospace so the layout doesn't jitter. (Cross-phase note D-18: this minimal inline handler is the seed the Phase 2 governor generalizes — keep the countdown rendering decoupled from the timing source so Phase 2 can feed it.) |
| **Confirm dialog** | shadcn `Dialog`, max-width 400px, overlay dims the shell. Title (Heading) + body (Body) + right-aligned button row: neutral Cancel (autofocus) then the action button. Escape and overlay-click both cancel. Destructive variant colors only the action button red. |
| **Identity display** | Horizontal block: avatar (48px circle, accent ring) + two-line stack: line 1 = display name (Heading) with a green "Signed in" check; line 2 = `@username` (monospace, muted). When avatar is missing, show initials on a slate-200/slate-700 circle (no broken image, no empty ring). Lives prominently at the top of the authenticated shell. |
| **App shell layout** | Full eventual layout scaffolded now: a slim top header band (secondary surface) carrying the app name + the identity display on the right and a settings/menu trigger (gear icon, ≥44px) that houses Log out; a main content area with the stubbed workflow regions (placeholder target-input area, placeholder group-list area) rendered as muted, clearly-labeled empty states — visibly inert, not fake-interactive. |

## Notes for Planner

- **shadcn init is the first UI task.** Run `npx shadcn init` (style new-york, base color slate, CSS variables on), then `npx shadcn add button input label select dialog alert avatar command`. After init, write the resolved preset string into this file's frontmatter and set `shadcn_initialized: true`.
- **Bundle Inter offline** via `@fontsource/inter` — do not load fonts from a CDN; an Electron tool must work without network for its own chrome.
- **Dark mode tokens are defined now** even though no toggle ships — wire the OS-appearance follow so Phases 3/4/6 inherit dark mode with zero extra work.
- **Cross-phase (D-18):** the live-countdown pattern's timing source should be injectable so the Phase 2 rate-limit governor can drive it without UI rework.
- **No API jargon reaches users** — the copywriting table is the canonical translation layer from GramJS error codes to human language.

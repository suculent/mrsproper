# Phase 5 — UI Design Contract

> Visual and interaction contract for the Removal Execution Engine (RMV-01, RMV-02, EXE-04, EXE-05). Generated by gsd-ui-researcher (autonomous mode). Verified by gsd-ui-checker.
>
> **This phase inherits the Phase 1 design system wholesale** (restated in the approved `03-UI-SPEC.md` / `04-UI-SPEC.md` and `04.1-UI-SPEC.md`). Tokens below are restated for executor convenience, not re-decided.
>
> **Scope is deliberately minimal — this is an engine phase.** The contract covers ONLY: (1) per-group removal status rendering on the existing GroupRow checklist rows + a progress indicator in the membership-scan visual language, (2) the minimal destructive-confirm dialog (LogoutDialog analog), (3) the persisted per-group report display (summary band + per-row outcomes + retry affordance), (4) PEER_FLOOD hard-stop, Stop removal, and Resume/Discard states, and (5) all copy strings in a `removalCopy.ts` module. **NO kick/ban selector ships this phase** (Phase 6 wizard) — the engine takes a severity parameter, hardcoded to **'ban'** for Phase 5 manual verification (user decision in CONTEXT.md). Copy for both severities is defined now so Phase 6 flips a parameter, not strings.


- Title (`text-heading`): `"Ban {name} from {N} group{s}?"` (kick: `"Remove {name} from {N} group{s}?"`)
- Identity block: 36px avatar (initials fallback, `AVATAR_COLORS[id % 7]`, duplicated per PATTERNS.md), name `text-label font-semibold`, identity line `@{username} · ID {id}` in mono `text-label text-muted-foreground` (ID always shown — TGT-03 anchor)

- Phase 5 hardcoded severity is **'ban'** — the dialog renders the ban variant during this phase's manual verification; both string variants live in `removalCopy.ts`.

## Report Display (per-group outcomes + summary band)

The per-group report (EXE-05) is persisted in the job file by the engine (audit trail — exact schema is planner discretion). The renderer shows it as:

1. **Per-row outcomes** — the GroupRow status icons + sublines from the table above persist after the run ends (they ARE the per-group report rows).
2. **Summary band** — replaces the progress indicator in the same slot when the run reaches `complete`, `stopped`, or `hard-stopped`:

```
Removed 9 · Already gone 1 · Failed 1 · Skipped 1
1 removal failed. You can retry it in the list.
Finished 14:32
```

- Counts line: `text-label text-foreground font-semibold` for the numbers, `text-muted-foreground` for the labels and `·` separators. Zero-count categories are omitted (e.g. no "Skipped 0").
- Failed follow-up line (only when failed > 0): `"{N} removal{s} failed. You can retry {them/it} in the list."` — `text-label text-muted-foreground` (parallels the Phase 4 scan failedN line)
- Stopped variant prepends: `"Removal stopped — {processed} of {N} processed."` — `text-label text-muted-foreground`
- Timestamp: `"Finished {HH:mm}"` (locale time, `Intl.DateTimeFormat` short time) — `text-label text-muted-foreground`
- On app relaunch with a finished job in the job file, the summary band + row outcomes rehydrate for the same target (planner discretion on rehydration mechanics; visual contract identical).

3. **Per-row retry affordance** — failed rows show the inline `retry removal` link (see status table). Clicking it re-runs the removal for that single group through the engine (generation-guarded per CR-02 lessons), with the row flipping to `removing` then its new outcome; the summary counts update. No re-confirmation dialog — the run was already confirmed and retry stays within its scope (CONTEXT: mirrors the membership-scan retry pattern).

## PEER_FLOOD Hard-Stop & Abort States

### PEER_FLOOD (EXE-03 surfaced in removal context)

When the governor classifies PEER_FLOOD mid-job, the engine hard-stops and checkpoints (CONTEXT). The progress indicator is replaced by a destructive Alert band (LogoutDialog warning-banner treatment) in the same slot:

- `<Alert variant="destructive" className="bg-destructive/10 border-destructive/30" role="alert" aria-live="assertive">` with `AlertTriangle` (`h-4 w-4`)
- Heading-weight first sentence + body: `"Telegram has flagged this account for too many actions. Wait a few hours before resuming — your progress is saved and the job can continue from where it stopped."` — `text-body`
- Processed rows keep their outcomes; the in-flight/unprocessed rows revert to the `queued` look (checked, disabled) — they are NOT marked skipped (the job is resumable, unlike a user stop)
- The summary band is NOT shown while the PEER_FLOOD banner is up (the banner owns the slot); resume happens via the on-launch ResumeJobDialog or a `"Resume removal"` destructive `size="sm"` button inside the banner (explicit click = explicit consent; no silent auto-resume)

### Stop removal (user abort)

- Current group's call finishes; remaining rows flip to `skipped`; checkpoint preserved; summary band renders with the stopped variant line. Job remains resumable via the same Resume path (resuming processes only `skipped`/unprocessed groups).

### Resume / Discard on launch (`ResumeJobDialog.tsx`)

On launch, if the job file holds an incomplete job (CONTEXT — no silent auto-resume for a destructive action):

- Dialog `sm:max-w-[400px]`; Title (`text-heading`): `"Finish removing {name}?"`
- Description (`text-body`): `"{X} of {N} groups were processed before the run stopped. Resuming continues from the first unprocessed group."`
- Footer: `<Button variant="outline" autoFocus>` — `"Discard job"` (safe default keeps the destructive action opt-in); `<Button variant="destructive">` — `"Resume removal"`
- Discard archives/clears the incomplete job (engine concern); Resume re-runs from the first unprocessed group with the progress indicator picking up at `{X}/{N}`.

### Target change during a run

"Change target" (TargetCard) is **disabled while a run is active** (`running`/`stopping`), with `title`/tooltip `"Stop the removal first"`. This resolves CONTEXT's open integration question (refuse vs abort-with-checkpoint) in favor of refuse — the least surprising behavior for a destructive in-flight job. `TARGET_RESET` therefore never fires mid-run from the UI; the main-process handler still defensively aborts-with-checkpoint if reached (CR-01 belt-and-suspenders).

## Interaction Contract

| Pattern | Contract |
|---------|----------|
| **Run lifecycle** | `idle → confirming → running → (complete \| stopped \| hard-stopped)`; retry of a single failed group: that row `failed → removing → outcome` without leaving the report state. Resume: `stopped/hard-stopped → running` from the first unprocessed group. |
| **Checklist lock during run** | All checkboxes disabled (queued rows show checked+disabled); run-trigger hidden; Refresh button disabled (`aria-disabled`, tooltip "Removal in progress"); filter input N/A (checklist mode has no filter); sort toggle remains enabled (visual-only reorder — execution order stays checklist enumeration order regardless, per CONTEXT). |
| **Sequential visibility** | Exactly one row in `removing` at any time; outcomes appear in enumeration order as each group checkpoints (live progress, EXE-04). |
| **Stop semantics** | Stop removal → current call finishes → remaining rows `skipped` → summary band (stopped variant). Stop button disabled+"Stopping…" in between. |
| **PEER_FLOOD semantics** | Hard-stop, destructive banner replaces progress, unprocessed rows revert to queued (not skipped), resumable explicitly. |
| **Retry generation guard** | Per-row retry captures the job generation before await (CR-02); a stale retry result from a discarded job never renders. |
| **Target change** | Disabled while running/stopping ("Stop the removal first"); after a finished run, Change target clears removal state + summary band along with the Phase 4 checklist reset (D-13 extension). |
| **Keyboard** | Dialogs: Radix focus trap, Esc dismisses to the safe outcome (no run start / no resume); Tab order puts the neutral button first (autofocus). Failed-row retry links are buttons reachable by Tab, Enter activates. Stop removal reachable by Tab during a run. |

## Accessibility Contract

- Progress wrapper: `role="status" aria-live="polite"` — "Removing {name} from group X of N" announced as it advances (matches scan precedent)
- PEER_FLOOD banner: `role="alert" aria-live="assertive"` (matches LogoutDialog warning banner)
- Status icons: `aria-hidden="true"` — sublines carry the meaning as visible text (read naturally, no aria-describedby needed)
- Queued rows: `<Checkbox disabled>` announces as unavailable; `aria-label` unchanged ("{groupName} — include in removal")

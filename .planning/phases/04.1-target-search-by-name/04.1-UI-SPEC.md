# Phase 4.1 — UI Design Contract

> Visual and interaction contract for Target Search by Name (TGT-05). Generated by gsd-ui-researcher (autonomous mode). Verified by gsd-ui-checker.
>
> **This phase inherits the Phase 1 design system wholesale** (restated in `03-UI-SPEC.md` and `04-UI-SPEC.md`, both approved). Tokens below are restated for executor convenience, not re-decided. ## Mode Detection Contract (extends Phase 3 D-01)

Detection runs on the normalized input (after existing URL/`@` stripping), in this priority order:

1. Empty → `none`
2. Starts with `+` → `phone-international`
3. All digits → `phone-bare`
4. **Contains whitespace between tokens, OR a trailing space, OR any character outside `[a-zA-Z0-9_]` (diacritics like "Novák", apostrophes, hyphens, non-Latin scripts) → `name`**
5. Single token of `[a-zA-Z0-9_]` only → `username` (unchanged)

Rationale and consequences (researcher discretion, derived from CONTEXT "input containing a space (or text not matching username/phone patterns)"):
- "Anna Nováková", "anna novak", "Novák", "O'Brien" → Name mode automatically.
- A single ASCII token ("anna") stays Username mode — the deterministic escape hatch for single-token name search is a **trailing space** ("anna "), which flips the chip to Name. The trimmed token is the query (single token allowed per CONTEXT).
- The username-not-found error copy gains a pointer to this path (see Error states) so users who typed a bare first name aren't dead-ended.
- The mode chip stays non-interactive (`pointer-events-none`, decorative, `aria-hidden`) — consistent with existing chips; the `aria-live` sr-only announcement gains "Name search mode detected".

**Name mode chip:** lucide `User` icon (`h-3.5 w-3.5`) + "Name" — same right-edge muted treatment as the Username/Phone chips.

**Validation (client-side, pre-dispatch):** trimmed query must be ≥ 2 characters. Matching is case-insensitive (server-side for supergroups via `ChannelParticipantsSearch`; client-side token-prefix, case-insensitive, for basic groups — keep behavior uniform per CONTEXT discretion note).

**Dispatch:** search fires ONLY on Find click or Enter (D-03 — no API calls while typing). Exactly one search run per dispatch; a new dispatch aborts and clears the previous run (generation guard).

## Search Progress Indicator

Mirrors the Phase 4 membership-scan pattern, placed in the left pane between the Find button and the candidate list.

```
Searching group 12 of 47…                    [Cancel]
[▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░]  h-1 bar
```

- Label: `"Searching group {X} of {N}…"` — `text-label text-muted-foreground` (exact wording locked by CONTEXT)
- Progress bar: `h-1 bg-muted rounded-full` track, `bg-primary` fill, `transition-[width] duration-200`, width `{X}/{N} * 100%`
- **Cancel**: ghost button (`variant="ghost" size="sm"`, `text-label text-muted-foreground hover:text-foreground`), label "Cancel", right-aligned on the label row. Aborts remaining group searches (MembershipScanner abort/generation-guard pattern). Candidates found so far **remain visible and selectable**; a muted line replaces the progress indicator: "Search stopped — {N} found so far."
- Wrapper: `role="status" aria-live="polite"` (matches Phase 4 scan progress)
- Candidates stream in below the bar as they're found and are **clickable immediately during the scan** (mirrors Phase 4 D-06 interactivity-during-scan)
- Groups are searched in enumeration order; ALL enumerated groups are searched, including no-ban-rights groups (CONTEXT — identification matters even where action isn't possible)
- Find button is disabled while a scan runs (Cancel is the only control); input stays editable
- FLOOD_WAIT mid-scan: governor absorbs it; the progress label row gains a muted subline "Telegram asked us to slow down — resuming automatically." with the existing monospace `FloodCountdown` when `governorFloodRemaining > 0`. The bar holds its width. No error styling — this is normal pacing, not a failure.

## Candidate List & Row Specification

Container: `rounded-lg border divide-y divide-border max-w-[560px]`, md gap above.

### Candidate row (mirrors GroupRow geometry)

```
┌──────────────────────────────────────────────────────────┐
│ [avatar 36px]  Anna Nováková                             │
│                @anovak · ID 12345678                     │  mono, muted
│                Found in: Brno Admins, Crypto CZ +3 more  │  muted
└──────────────────────────────────────────────────────────┘
```

- The entire row is a `<button type="button">`: `min-h-[56px] px-4 py-3 flex items-center gap-3 w-full text-left hover:bg-accent/10` + standard focus-visible ring
- Avatar: 36px (`h-9 w-9`), `rounded-full`; **lazy-loaded** via governor-routed `downloadProfilePhoto` for visible candidates; until loaded (or when absent) show colored-initials fallback — `AVATAR_COLORS[id % 7]`, white semibold, first letter of first + last word (TargetCard `getInitials` logic, duplicated)
- Name: `text-label font-semibold text-foreground truncate`
- Identity line: `@{username}` (mono) when present, ` · ` separator, `ID {id}` (mono) — `text-label font-mono text-muted-foreground truncate`. When no username: ID only. Never hide the ID (it's the disambiguation anchor).
- Found-in line: `text-label text-muted-foreground truncate` — "Found in: {first 2 group titles}" + ", +{N} more" when found in more than 2; full list in the row's `title` attribute
- Ordering: by found-in count descending, then name A–Z (CONTEXT); dedup by numeric user ID with merged found-in lists
- Deleted accounts surfaced by search: show lucide `Ghost` (24px, `text-muted-foreground` on `bg-secondary` fill) instead of initials, matching TargetCard's deleted treatment

### Selection

- Click → the clicked row shows `Loader2` spinner (16px, replaces nothing — appears right-aligned in the row), all rows disable, and the candidate resolves through the existing TargetResolver path by numeric ID (exactly-once)
- On resolve success: candidate list and progress UI unmount; TargetInput collapses to its one-line mono summary; TargetCard renders with the standard confirm gate — **identical landing to username/phone resolution**
- On resolve failure: list re-enables; inline error below the input per the existing resolve error pattern

### Cap notice (exactly 100 — user-specified)

When results hit 100, stop appending and render below the list:
`"Showing first 100 — refine your search."` — `text-label text-muted-foreground`, `px-4 py-2`. The scan keeps running only if needed for found-in merging of already-listed IDs; otherwise it may short-circuit (planner/executor discretion — visual contract is just the notice).

### Soft per-group failure note

After scan completion, if some groups errored: `"Couldn't search {N} group{s}"` — `text-label text-muted-foreground`, below the list. Non-blocking, no retry affordance in this phase (skip-and-continue isolation per CONTEXT; unlike membership verification, a missed group here is recoverable by re-searching).

## Interaction Contract

| Pattern | Contract |
|---------|----------|
| **Explicit dispatch (D-03)** | Name search fires only on Find click or Enter. No debounce, no search-while-typing. |
| **Generation guard / re-search** | A new Find aborts the running scan, clears prior candidates, and starts fresh (no caching — D-15 consistency). Stale results from a previous generation never render (CR-02 lesson). |
| **Target change / reset (CR-01)** | `TARGET_RESET` (Change target, or starting a username/phone resolve) aborts any in-flight name search and clears all candidates — stale candidates never survive a target change. |
| **Interactive during scan** | Candidates are clickable as they stream in (mirrors Phase 4 D-06). Clicking mid-scan aborts the remaining scan, then resolves the pick. |
| **Cancel** | Aborts remaining group searches; partial candidates stay selectable; progress replaced by the "Search stopped" line; Find re-enables. |
| **Selection collapse** | Pick → resolve via TargetResolver by numeric ID → candidate UI unmounts → TargetCard confirm gate. Identical post-resolution flow to username/phone (input collapses to mono summary; GroupsPane flips to checklist only after confirm). |
| **Avatar lazy-load** | Governor-routed `downloadProfilePhoto` per visible candidate; initials render instantly, photo swaps in when downloaded; no layout shift (fixed 36px). Avatar downloads are lowest priority — they must never delay group searches in the serialized queue. |
| **Keyboard** | Tab reaches each candidate row (it's a button); Enter/Space selects; Escape while the scan runs triggers Cancel (researcher discretion — matches dialog-dismiss intuition); progress updates announced via `aria-live="polite"`. |

State machine (extends Phase 3's): `idle → searching → (cancelled | complete) → candidate-picked → resolving → resolved(card) → confirmed`; any error → `idle-with-error`; `TARGET_RESET` from anywhere → `idle`.

## Accessibility Contract

- Progress wrapper: `role="status" aria-live="polite"` — counter changes announced
- Candidate rows: native `<button>` elements, `aria-label="{name} — found in {N} of your groups"`

- Spinner on a resolving row: `aria-hidden`; the row's accessible name is unchanged; list disablement uses `disabled` on the buttons

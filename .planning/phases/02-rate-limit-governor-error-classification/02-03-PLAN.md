## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SessionManager._fetchIdentity → governor.run() | getMe/downloadProfilePhoto calls now serialized — no direct client access for post-auth operational calls |
| SessionManager.logout → governor.run() | auth.LogOut invoke now serialized — consistent with post-auth call policy |
| TelegramClient floodSleepThreshold=0 | GramJS will NEVER silently absorb FLOOD_WAIT — all flood errors reach the governor for D-09 countdown emission |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Elevation of Privilege | SessionManager post-auth calls | mitigate | _fetchIdentity and logout route through governor.run() — these calls are now subject to the serialization and rate-limit policy of EXE-01; direct _client.getMe() / _client.invoke() paths removed from post-auth context |
| T-02-09 | Denial of Service | floodSleepThreshold=0 | mitigate | Setting threshold=0 ensures GramJS never silently absorbs any FLOOD_WAIT; every flood event is surfaced to the governor so D-09 (always emit countdown) and D-12 (ceiling check) are applied — no silent blocking in main process |
| T-02-10 | Tampering | D-06 auth bypass exception | accept | Interactive auth steps (submitPhone, submitCode, submitPassword) remain outside governor per D-06 — documented exception. Login is human-paced and effectively serial; not a volume flood vector. If login FLOOD_WAIT handling breaks due to threshold=0, the existing FloodWaitController path in SessionManager/AuthFlow handles it. |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this plan — SessionManager.ts and main/index.ts modifications use only already-installed dependencies |
